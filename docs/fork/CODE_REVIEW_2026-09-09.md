# H-OpenTypeless 코드·안정성·메모리 검토

검토일: 2026-09-09. 대상: `/Users/ryuhoil/syncthing/workspace/h-opentypeless`, HEAD `b371c84`와 현재 미커밋 변경을 포함한 작업 디렉터리. 기존 모바일 프로젝트는 대상이 아니다. 기능 수정·배포는 하지 않았으며 VAD 도입은 보류했다.

## 판단

대기 상태에서 데스크톱 본체가 지속적으로 CPU를 많이 쓰거나, 짧은 관찰 중 메모리가 계속 증가한다는 증거는 없었다. 다만 키체인 대기 처리, 음량 이벤트 구독 범위, 오디오 과부하 시 오류 처리에는 개선할 구체적인 문제가 있다. 로컬 실행에서 큰 메모리 비용은 별도 STT·LLM 프로세스에서 발생한다. 이 검토는 무결함 인증이나 장시간 누수 검증을 대신하지 않는다.

## 우선순위별 발견 사항

### P1 — 키체인 응답 지연이 녹음 시작·중지 경로를 붙잡을 수 있음

- 근거: `src-tauri/src/pipeline.rs:1074`에서 시작 준비 동안 `pipeline_lock`을 보유하고, `:1154`에서 동기식 `resolve_stt_config_secret`을 호출한다. 중지는 `:1769`에서 같은 잠금을 기다린다. LLM 처리 `:2124`와 Ask 경로에도 동기 자격 증명 조회가 있다.
- `credentials.rs`의 시스템 키체인 호출에는 이 경로 자체의 시간 제한이 없다. OS 권한 응답 등이 늦으면 비동기 실행 스레드를 점유하고 사용자는 시작 또는 중지가 멈춘 것처럼 느낄 수 있다.
- 같은 설치 빌드의 기존 스택 샘플에서 `start_with_options → resolve_stt_config_secret → SecKeychainFindGenericPassword → SecurityServer → mach_msg` 대기가 관찰됐다. 항상 발생하는 장애라는 뜻은 아니다.
- 권장: 모바일 서버의 `extensions/mobile/processing.rs:17-38`처럼 별도 blocking 작업, 동시 실행 제한, 호출자 대기 시간 제한을 공통 서비스로 제공한다. 시간 제한 이후에도 OS 호출 자체는 계속될 수 있으므로 실행 허가는 실제 반환까지 유지하고, 늦게 온 결과는 세션 번호로 폐기해야 한다. 대기 중 취소와 재시작도 검증한다.

### P2 — 음량 변화가 상위 화면의 불필요한 렌더링을 유발함

- 근거: `src/hooks/useTauriEvents.ts:51-72`는 setter만 사용하면서 `useAppStore()` 전체를 구독한다. 이 훅을 `src/App.tsx:39,121`의 메인 화면과 캡슐에서 사용한다.
- 녹음 음량은 일반 받아쓰기에서 50ms 간격, Ask에서 약 33ms 간격으로 전달된다. 음량 값이 바뀌면 훅을 사용하는 컴포넌트도 갱신 대상이 된다. 실제 DOM 전체가 매번 변경된다는 뜻은 아니다.
- 재현: 이 훅을 사용하는 테스트 컴포넌트에서 음량을 서로 다른 값으로 20회 갱신하자 추가 렌더링이 20회 발생했다. 실제 앱의 프레임 손실이나 CPU 상승 폭을 측정한 결과는 아니다.
- 권장: 안정적인 개별 action selector 또는 `getState()`로 이벤트 핸들러를 구성하고, 파형 컴포넌트만 필요한 음량 상태를 구독한다. React Profiler로 메인 화면과 캡슐을 각각 비교한다.

### P2 — 오디오 큐 과부하 시 데이터 손실을 알리지 않음

- 근거: `src-tauri/src/audio/capture.rs:327-330`은 버퍼에서 청크를 제거한 다음 `try_send` 결과를 버린다. 큐가 가득 차거나 수신기가 닫히면 해당 청크는 복구되지 않는다. `:334`의 장치 콜백 오류도 로그만 남긴다.
- 큐는 약 60초 분량으로 제한되어 있으므로 일반적인 짧은 지연이 바로 손실로 이어지지는 않는다. 그러나 수신 처리가 오래 막히면 녹음 중 UI가 유지되면서 일부 발화가 사라질 수 있다. 실제 사용자 녹음에서 이 조건을 재현한 것은 아니다.
- 권장: overflow·수신 종료·장치 오류를 파이프라인에 전달하고 세션별 손실 수치를 남긴다. 데이터 손실 후 결과를 조용히 정상 제출하지 않도록 한다. 오디오 콜백에서 blocking send로 바꾸면 안 된다. 이후 필요하면 할당과 잠금을 줄이는 재사용 버퍼를 검토한다.

## 메모리·CPU 관찰

실행 중인 설치 앱과 모델 서버를 종료하거나 새 녹음을 시작하지 않고 관찰했다. 설치 앱은 개발용 debug 빌드이므로 release 성능과 동일하다고 볼 수 없다. 현재 작업 디렉터리 테스트와 실행 바이너리 측정은 별도의 증거다.

| 본체 physical footprint | 43.6M, peak 46.0M | WebKit 자식·외부 모델을 포함한 앱 전체 값이 아님 |

RSS, footprint, 모델 size 및 통합 메모리/GPU 값은 단순 합산하면 안 된다. 발견된 WebKit helper 4개는 각각 약 42~108MiB RSS였으나 모두 H 소유라고 확정하지 못해 앱 전체 메모리 합산에서 제외했다. 큰 가상 주소 공간은 실제 RAM 사용량으로 해석하지 않았다.

누수 후보에는 NSXPCConnection 등의 객체가 포함된다. 현재 실행에는 allocation stack 기록이 없어 앱 코드와 시스템 프레임워크 중 어디에 책임이 있는지 확정할 수 없다. 고정 초기화 비용인지 녹음 반복에 따라 증가하는 누수인지도 별도 반복 측정이 필요하다. 따라서 “누수 없음” 또는 “14KB 전부 앱 결함”이라는 결론은 내리지 않는다.

## 구조상 확인한 보호 장치와 비용

- 마이크 소유권을 CaptureLease로 제한하며, 네이티브 종료가 끝나기 전 새 캡처가 겹치지 않도록 보호한다. 종료 시간 초과 시 무조건 다시 여는 방식도 피한다.
- 오디오 큐, STT 업로드, HTTP/SSE 응답에는 크기 제한이 있다. 무제한 버퍼보다 안전하지만 WAV 생성·multipart 복사 등은 제한 범위 안에서도 일시적인 메모리 증가를 만들 수 있다.
- 캡슐·테두리 효과에는 타이머/리스너 정리와 세션 세대 검사 등의 방어 코드가 있다. 전체 화면 애니메이션의 실제 GPU·배터리 비용은 녹음 중 별도 측정이 필요하다.
- 여러 WebView와 공통 프런트엔드 번들은 기본 메모리 비용을 가진다. 효과를 사용하지 않을 때 지연 생성하는 방안은 검토할 수 있으나 현재 측정만으로 이것이 주요 병목이라고 단정하지 않는다.
- Android 로컬 모델은 별도 서비스 프로세스를 사용하고, 종료·취소 시 프로세스 종료 및 바인딩 해제를 수행한다. Gemma Engine/Conversation은 try-with-resources로 닫는다. 작업마다 모델 초기화를 반복하므로 메모리 회수와 첫 응답 지연 사이의 절충이 있다. 이번 Android 검토는 정적 검토이며 실기기 메모리·발열 검사는 하지 않았다.
- 받아쓰기와 Ask의 큰 상태 처리 코드 및 중복된 자격 증명·오디오 처리 경로는 유지보수 부담이다. 위 문제를 먼저 고친 뒤 공통 자원 관리 단위로 점진적으로 나누는 편이 좋다.

## 후속 개선 구현 (같은 날)

위 검토 결과를 순서대로 반영했다. Android 앱 소스는 이번 후속 작업에서 변경하지 않았다.

- 키체인: 공통 `read_config_secret` 서비스에서 blocking worker 1개 제한과 20초 제한을 적용했다. 취소·시간 초과 후에도 실행 중인 OS 호출이 permit을 유지하여 재시도에 따른 스레드 누적을 막는다. 받아쓰기 준비 중 중지는 취소로 처리하고, Ask 시작 세대 검사로 이전 요청이 새 요청을 정리하는 것을 방지한다. 맥의 모바일 요청 서버도 같은 서비스를 사용한다.
- 화면: `useTauriEvents`가 전체 Zustand 상태를 구독하지 않고 안정적인 action 참조를 사용한다. 음량 100회 변경에서 상태는 정상 갱신되고 훅 호스트 추가 렌더링은 0회였다.
- 오디오: 큐 포화·수신 종료·네이티브 마이크 오류를 최초 오류로 보존한다. 콜백은 원자 상태와 알림만 갱신하고, 캡처 스레드가 종료를 수행한다. STT 전송/종료 호출을 기다리는 중에도 오류 감시가 작업을 중단한다. 받아쓰기는 취소 후 오류를 알리고, Ask는 기존 오류 처리 경로로 넘겨 불완전한 결과가 입력되지 않도록 한다. 정상 종료는 오류와 구별한다.
- Ask 작업 완료 신호는 기다리는 쪽이 아직 없더라도 보존되도록 `notify_one`으로 바꿨다.

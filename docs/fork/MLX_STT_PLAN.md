# 내장 Qwen STT의 환경 감지와 MLX 실행 계획

2026-09-10 · 기준 커밋 `8b46610`에서 작성한 계획. 사용자 후속 승인으로 구현을 진행했으며 결과와 차이는 [MLX_STT_VERIFICATION.md](MLX_STT_VERIFICATION.md)에 기록한다. 아래 내용은 최초 계획이다.

## 결정과 범위

호환되는 Apple Silicon Mac에서는 내장 Qwen3-ASR을 MLX GPU로 실행한다. 사용자는 앱만 실행하고 모델을 선택해서 다운로드하면 된다. 별도 서버 기동, Homebrew, pip 설치를 요구하지 않는다. 기존 외부 STT 제공자와 LLM/Ollama 설정은 유지한다.

현재 내장 Qwen은 C CPU/BLAS 엔진이다. 예전 외부 Qwen 서버는 MLX GPU를 사용했다. 이번 작업은 C 엔진 옵션 변경이 아니라 MLX 실행 환경과 앱 전용 워커를 추가하는 작업이다. 제거된 옛 외부 서버를 복원하는 방식으로 진행하지 않는다.

첫 배포는 macOS arm64 앱에 전용 Python·MLX 실행 환경을 함께 포함한다. 별도 엔진 팩 다운로드/업데이트 채널은 후속 과제로 둔다. 모델은 지금처럼 별도 다운로드한다. DMG 용량 증가량과 최소 macOS 버전은 패키징 시제품으로 측정하고 확정한다.

| 환경 | 자동 모드의 Qwen 처리 |
|---|---|
| 호환되는 Apple Silicon Mac, MLX GPU 검사 성공 | MLX GPU |
| Intel Mac 또는 MLX 요구 조건 미충족 | 지원되는 기존 CPU 엔진, 이유 표시 |
| Linux | 기존 CPU 엔진 유지; 이번 범위에 Linux GPU 추가 없음 |
| Windows | 현재 Qwen 미지원 유지; 내장 Whisper 제공 |

MLX 프레임워크 자체의 Linux 지원과 이번에 사용하는 Apple Silicon용 Qwen 구현의 지원 범위는 구분한다. Whisper 엔진은 이번 작업에서 변경하지 않는다. Windows/Linux 구조와 빌드는 점검하되 실기기 검증은 사용자 요청대로 나중에 한다.

## 1. 환경 감지와 사용자 설정

설정은 `자동(권장) / MLX GPU / CPU`로 제공하며 실제 실행 엔진을 별도로 표시한다.

1. OS 버전, 하드웨어와 실행 프로세스 아키텍처, 물리 메모리, 번들 런타임 버전을 확인한다. Rosetta로 실행 중인 경우도 구분한다.
2. 별도 워커에서 MLX import와 작은 GPU 연산의 실제 평가를 제한 시간 안에 검사한다. arm64라는 이유만으로 GPU 사용 가능으로 표시하지 않는다.
3. 실제 모델 로드는 별도 준비 단계로 취급한다. GPU 검사 성공은 1.7B 모델의 메모리 확보까지 보장하지 않는다.
4. 앱 시작 시 모델 전체를 로드하지 않는다. 최초 녹음 때 준비를 시작하며 마이크 시작을 막지 않는다. 준비 실패/지연 상태는 명확히 표시한다.

자동 모드에서 환경상 미지원이면 CPU를 선택하고 사유를 보여 준다. 지원 검사 후 MLX가 실행 중 실패하면 조용히 CPU로 바꾸지 않는다. `재시도 / CPU로 처리`를 제공한다. 강제 MLX 모드는 실패 사유를 표시한다. 사용자의 모델 크기, STT 제공자, LLM 모델을 자동 변경하지 않는다.

실패한 요청의 음성은 기존 제한 내에서만 재시도를 위해 보관하고, 취소/종료/정해진 보관 기한에는 해제한다. 오류 안내 때문에 무기한 보관하지 않는다.

공식 MLX 설치 문서는 Apple GPU 경로에 Apple Silicon, 네이티브 Python 및 macOS 요구 조건을 명시한다. 실제 제품 최소 버전은 선택한 고정 wheel과 의존성의 요구 조건 및 실기기 검사를 기준으로 결정한다. [MLX 설치 문서](https://ml-explore.github.io/mlx/build/html/install.html)

## 2. 앱 내부 구조와 배포

```text
기존 데스크톱 / Ask / 모바일 입력
             ↓
기존 내장 STT 제공자와 단일 작업 제어
             ↓
환경 감지 + 엔진 선택
       ┌─────┴─────┐
   MLX 워커     기존 CPU 엔진
       └─────┬─────┘
          전사 결과
             ↓
기존 LLM 다듬기와 텍스트 출력
```

- `extensions/local_stt` 아래에 환경 감지, 공통 엔진 인터페이스, MLX 워커 관리자와 검증 캐시를 분리한다. 기존 `SttProvider` 경계를 유지해 업스트림 파이프라인 변경을 최소화한다.
- 앱이 자식 프로세스로 전용 Python 워커를 실행한다. 통신은 표준 입출력의 길이가 제한된 메시지와 PCM 데이터로 한다. 포트, HTTP 서버, LaunchAgent를 추가하지 않는다.
- 요청 ID와 실행 세대 번호로 늦게 도착한 결과를 폐기한다. stdout은 프로토콜 전용, stderr는 크기가 제한된 진단용으로 구분한다. 음성·전사문·인증 정보는 로그에 남기지 않는다.
- Python과 필수 라이브러리, Metal 리소스만 재배치 가능한 번들로 준비한다. 개발자의 venv를 그대로 복사하지 않는다. FastAPI, 마이크 캡처, PyTorch 등 불필요한 선택 의존성은 넣지 않는다.
- 버전·해시·라이선스 목록을 고정한다. Python 실행 파일, 동적 라이브러리, 워커 리소스와 최종 앱의 서명을 검사한다. 기존 credential helper의 내용과 서명은 유지한다.

실행 라이브러리 후보는 `mlx-qwen3-asr`의 Session API다. Session이 모델을 재사용하므로 매 녹음마다 프로세스와 모델을 새로 만드는 비용을 줄일 수 있다. 버전은 구현 시 시험한 정확한 버전/커밋으로 고정한다. [Session API](https://github.com/moona3k/mlx-qwen3-asr#session-api-recommended-for-repeated-calls)

## 3. 이미 다운로드한 모델 재사용

- 현재 Qwen 0.6B/1.7B 원본 safetensors를 우선 재사용한다. 사용자 모델 디렉터리를 다른 곳으로 이동하거나 가중치를 다시 다운로드하지 않는다.
- 현재 카탈로그에 없는 `tokenizer_config.json` 등 필요한 보조 파일만 고정 리비전과 해시로 추가한다. 양쪽 엔진에서 실제 전사해 호환성을 확인한다.
- 워커에는 검증된 로컬 경로만 전달하고 라이브러리의 암묵적 네트워크 다운로드를 차단한다. 준비된 모델은 인터넷 없이 실행되어야 한다.
- 현재 `verified` 표식은 모델 메타데이터 전체에 의존한다. 엔진 정보나 보조 파일 추가 때문에 기존 가중치가 미설치로 처리되지 않도록 파일별 검증 기록으로 마이그레이션한다. 기존 파일을 검증해 재사용하며 삭제 후 재다운로드하지 않는다.
- 최초 다운로드 및 최초 신뢰 확인 시 전체 SHA-256 검증을 유지한다. 같은 앱 세션에서는 파일 식별자·크기·변경 시각을 확인해 검증 결과를 재사용한다. 이는 악의적인 로컬 파일 변조를 완전히 차단하는 장치로 간주하지 않는다. 파일 교체/삭제/변경 시 무효화하고 수동 전체 검증을 제공한다.

로컬 모델 로딩과 tokenizer 보조 파일 처리는 라이브러리 구현을 확인한 뒤 고정 버전에 맞춰 통합한다. [모델 로더](https://github.com/moona3k/mlx-qwen3-asr/blob/main/mlx_qwen3_asr/load_models.py), [토크나이저](https://github.com/moona3k/mlx-qwen3-asr/blob/main/mlx_qwen3_asr/tokenizer.py)

## 4. 메모리·취소·종료 안정성

- 한 번에 워커 하나, 모델 하나, 요청 하나만 허용한다. 모델 로드와 추론은 같은 전용 스레드에서 직렬 처리한다.
- 모델은 반복 입력을 위해 잠시 유지한다. 초기 유휴 만료 후보는 2분이며 실제 측정 후 확정한다. 모델 상주 여부를 설정 화면에서 보여 준다.
- 메모리 압박 시 유휴 워커를 종료한다. 추론 중에는 진행 중 작업과 사용자의 취소를 구분하며, 제한 시간/심각한 자원 부족 시 실패를 알리고 정리한다. Ollama와 동시에 사용할 때도 측정한다.
- 취소 요청 후 제한 시간 안에 멈추지 않으면 워커를 종료하고 반드시 회수한 뒤 다음 작업을 허용한다. Python 취소만으로 진행 중 Metal 연산이 중단된다고 가정하지 않는다.
- 앱 정상 종료, 부모 프로세스 종료와 파이프 단절, 워커 장애에도 고아 프로세스가 남지 않도록 부모 생존 감시를 둔다. 추론 중 부모 종료도 검증한다.
- 모델 삭제/교체/선택 변경 전 해당 모델의 워커를 정지한다. 다운로드/검증/추론 간 기존 단일 작업 제어와 충돌하지 않도록 통합한다.
- 기존 120초 음성 제한과 버퍼·출력·작업 시간 제한을 유지한다. 실패와 재시도에서 워커, PCM, GPU 메모리가 누적되지 않아야 한다.

## 5. 순서와 완료 기준

### A. 기준 측정과 배포 가능성 확인

실제 앱에서 검증·모델 준비·STT·LLM·출력 시간을 분리 계측한다. 현재의 CPU 결과를 기준으로 남긴다. 작은 MLX 번들 시제품으로 GPU 연산, 모델 로드, 재배치, 서명, 최소 OS와 패키지 크기를 확인한다. 이 단계가 통과하기 전 자동 모드 기본값을 변경하지 않는다.

### B. 공통 엔진과 워커 수명 관리

기존 CPU 경로를 엔진 인터페이스에 연결하고 MLX 요청/취소/종료 프로토콜을 추가한다. 감지 실패·시간 초과·워커 종료·늦은 응답·중복 실행 회귀 테스트를 둔다.

### C. 모델과 반복 성능

기존 모델 재사용, 보조 파일 다운로드, 검증 기록 마이그레이션, Session 재사용, 유휴 종료와 메모리 압박 처리를 구현한다. 가중치 재다운로드 없이 업그레이드되는지 확인한다.

### D. 설정과 통합

자동/MLX/CPU와 실제 엔진·준비 상태·실패 사유를 표시한다. 데스크톱, Ask, 모바일 모두 같은 선택을 사용한다. LLM 설정과 지침, 포커스를 잃을 때 복사 창으로 이어지는 동작은 보존한다.

### E. 실제 검증 후 설치

- 동일 모델과 동일 한국어 음성 묶음으로 CPU/MLX를 비교한다. 짧은 문장, 개발 용어, 긴 음성을 포함하고 최초/반복 실행의 중앙값과 상위 지연을 따로 기록한다. LLM을 제외한 STT와 전체 입력 지연을 구분한다.
- 반복 녹음 20회 이상, 연속 취소/재시작, 긴 녹음, 모델 교체, 모바일 동시 요청, 앱 종료를 검사한다. 유휴 해제 후 메모리가 회수되고 반복마다 계속 증가하지 않아야 한다.
- 사용자 Python/Homebrew 및 옛 8765 서버가 없는 환경에서도 실행하고, 모델 준비 후 오프라인 동작을 확인한다. 공백/한글 경로와 실제 DMG 설치본을 검사한다.
- MLX 반복 실행 속도가 CPU 대비 개선되고 전사 품질에 뚜렷한 회귀가 없는지 확인한 뒤 호환 Mac의 자동 선택을 활성화한다. 검증 전 특정 배수의 속도 개선을 약속하지 않는다.
- 실제 Mac 검증 결과, 미검증 OS와 남은 제약을 기록한다. 사용자 일상 입력 확인 뒤 다음 작업으로 튜토리얼을 안내한다.

각 단계는 검토 가능한 별도 커밋 단위로 진행한다. 이번 요청에서는 계획 문서만 작성하며 구현·설치·커밋·푸시는 진행하지 않는다.

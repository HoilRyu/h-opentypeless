# 긴 음성 요청의 의미별 구조화

2026-09-10. `typeless-quality` 워크트리에서 기존 `structured` 스타일을 개선했다.

## 동작

말로 나열한 목적·요청·조건·역할·실행 시점을 해석해 다음 형식 중 필요한 것을 선택한다.

- 짧은 질문·단일 요청·조건부 대안: 평문.
- 하나의 설명: 문단. 길다는 이유만으로 할 일 목록을 만들지 않는다.
- 독립된 요청: 글머리표. 뒤에서 덧붙인 조건을 해당 요청에 연결한다.
- 실제 순서가 있는 작업: 번호 목록.
- 여러 종류의 내용이 섞인 긴 요청: 목적 문단과 필요한 소제목·목록.

[영상 9:40~10:20](https://www.youtube.com/watch?v=8yCyUD3Nsuk&t=580s)에서 관찰한 제작 조건·역할 구성·진행 방식의 구분을 참고했다. 영상의 내부 프롬프트나 원본 STT는 공개되지 않았으며, 제품 예시와 평가 입력은 별도로 작성했다. Typeless의 모델이나 설정을 복제했다는 의미가 아니다.

기존 지침은 실행할 요청을 같은 수준의 목록에 넣는 규칙이 중심이었다. 새 지침은 의미별 묶음, 조건의 연결, 현재 요청과 다음 단계의 분리를 명시한다. 제목과 목록 사용을 설명하는 문구만 늘리지 않고, 짧은 요청·질문·선택지·숫자 정정·작업 순서·긴 복합 요청의 입력/출력 예시를 추가했다.

## 적용 경로

`src-tauri/src/llm/h_polish.rs`의 `STRUCTURED`와 예시를 수정했다. 일반 받아쓰기의 기존 시스템 프롬프트 빌더와 한 번의 LLM 호출을 그대로 사용한다. 별도 분류 호출이나 두 번째 교정 호출은 추가하지 않았다. 내용 중 명령을 실제 실행하는 방식으로 바꾸지 않았다.

로컬 Ollama의 일반 구조화 받아쓰기는 생성 온도를 0으로 낮췄다. 온도 0.3의 반복 평가에서 이름의 어미나 말투가 달라지는 경우가 발견됐기 때문이다. `openai.rs`의 요청 생성 시 적용하며, 장면·번역·선택문·질문 모드와 원격 제공자는 기존 값을 사용한다. GLM 계열의 기존 공급자별 강제 설정은 계속 우선한다. 온도 0이 모든 환경에서 동일 출력을 보장한다는 뜻은 아니다. 이번 최종 비교는 프롬프트와 샘플링 설정을 함께 바꾼 결과다.

사용하려면 다듬기 스타일에서 **구조화**를 선택한다. 현재 새 설치의 기본 선택은 `clean`이며 이번 변경으로 사용자 설정이나 기본 선택을 바꾸지 않았다. `minimal`, `clean`, `professional`의 내보낸 프롬프트는 이전과 동일하다. 번역을 켠 구조화 모드에도 구조 규칙이 포함되지만 이번 모델 평가는 한국어 비번역 입력에 한정한다.

수동 장면이나 앱에 연결한 장면이 있으면 기존 우선순위에 따라 해당 장면이 출력 형식을 결정한다. 선택문 편집도 별도 계약을 유지한다. 구조화를 선택했는데 형태가 적용되지 않는 경우 장면 설정을 확인해야 한다. 기존 기록의 ‘결과 비교·다시 다듬기’에서 구조화를 선택하면 장면 없이 현재 모델로 원문을 재처리할 수 있다.

프롬프트는 저장소에 포함된다. 다른 컴퓨터에서도 해당 커밋을 가져와 빌드하면 같은 프롬프트가 사용된다. 선택한 스타일·모델·사전·개인 지침은 컴퓨터별 설정이므로 동일한 출력 자체까지 보장되지는 않는다.

## 비교와 보완

[평가 자료](../../evaluation/polish/structure.json)는 기존 16개와 새로 작성한 10개 문장으로 구성된다. 개발 중 이 결과를 보고 수정했으므로 최종 26개는 미사용 자료가 아니다. 별도 [4개 문장](../../evaluation/polish/structure-holdout.json)은 중간 개정 후 처음 시험했으나 말투·지시 대상 오류를 발견해 추가 수정에 사용했다. 따라서 이 4개도 최종 평가 시점에는 회귀 자료이며, 최종 결과를 미사용 자료의 성능으로 주장하지 않는다. 모두 원음 없는 합성·재구성 텍스트다.

중간 결과에서 다음 오류를 발견해 보완했다.

- ‘마지막 쪽’을 ‘마지막 장’으로 좁힘: 대략적인 위치·시점 표현을 보존하도록 명시.
- 정정 전 숫자를 함께 남김: 명확한 정정 전 내용 제거와 별도 숫자 정정 예시 추가.
- 나열한 이름을 문장의 수식어로 바꾸거나 첫 이름을 누락함: 뒤에서 붙는 ‘버튼 이름’ 설명을 앞의 열거와 연결하고 이름 개수를 확인하도록 보완.
- 존댓말 원고를 반말로 바꿈: 예시 뒤에 실제 원고의 어미와 부탁 강도를 보존하는 최종 지침 추가.
- 생략된 선택 대상을 잘못 채움: ‘제가 고른 다음’에 선택 대상을 임의로 추가하지 않고 원문 표현을 보존하도록 보완.
- 온도 0.3에서 반복 시 이름 어미가 달라짐: 로컬 Ollama의 일반 구조화 받아쓰기 온도를 0으로 낮추고 반복 검증.

`scripts/h-polish-eval.py`에 변경 전/후 Rust 빌더의 완전한 프롬프트를 비교하는 `--candidate-prompts`와 단독 반복 실행의 `--label`을 추가했다. 최소 구획·목록 수, 평문 여부도 보조 검사한다. 자동 검사를 통과해도 의미가 보존됐다고 판정하지 않는다.

## 실제 개선 결과 예시

영상의 구조를 참고해 새로 작성한 카드 이미지 요청에서 다음과 같은 출력이 나왔다. 아래는 해당 결과의 **구조와 주요 조건만 발췌**한 것으로, 전체 출력은 평가 결과 파일에 남긴다.

```text
분석 및 제작 조건:
- 참고 자료를 보고 색상 조합, 여백, 글자 크기 비율부터 분석해줘.
- 분량은 여섯 장을 넘기지 마.
- 첫 장은 관심을 끌게 하고, 마지막 쪽에는 구매 링크 안내를 넣어줘.

역할 구성:
- 기획 담당, 디자인 담당, 검수 담당을 생각하고 있어.
- 검수 담당은 참고 자료에서 뽑은 기준을 어기면 다시 수정하도록 해줘.

진행 순서:
1. 지금은 팀 구성안만 추천해줘.
2. 내가 다음에 시작하라고 하면 그때 제작해줘.
```

## 최종 검증

- 실제 제품 빌더에서 내보낸 프롬프트와 로컬 `gemma4:12b`, 온도 0으로 **30개 사례, 64회** 실행했다(26개 × 2회 + 추가 회귀 4개 × 3회). 모든 응답이 정상 종료됐다. 이 실행 범위에서 각 사례의 반복 출력은 같았다.
- 자동 경고는 **5/64회**다. 두 종류의 짧은 ‘선택지 추가 + 선택 기억’ 요청이 목록 대신 문장으로 남은 경우다. 이름이나 조건이 빠진 경고는 없었다. 경고를 통과로 처리하지 않았다.
- Codex가 원문과 결과를 대조했으며 최종 표본에서는 이름·숫자·부정·말투·현재 요청 범위의 변경을 발견하지 못했다. 독립된 사람의 블라인드 평가나 일반적인 정확도 보장은 아니다. 보고서 사례에서 금지 사항을 번호 목록의 다음 항목으로 두는 등 형식상의 개선 여지는 남는다.
- Rust **648 통과, 7 제외**, 평가 도구 Python **5 통과**. 실제 HTTP 요청 본문에 온도 0이 들어가는지, 장면·번역·선택문·질문·원격 제공자에는 적용되지 않는지 검증했다. 최종 내보내기 결과는 모델 평가에 사용한 프롬프트와 동일하다.
- 프롬프트 소스 및 제공자 파일의 Rust 형식 검사와 diff 공백 검사를 통과했다. 저장소 전체의 `cargo fmt --check`에는 변경하지 않은 기존 파일의 형식 차이가 남아 있다.

## 해석과 한계

모델 출력은 완전히 고정되지 않는다. 짧은 복합 요청이 목록 대신 문장으로 남거나, 희망형 부탁이 직접적인 부탁으로 바뀌는 작은 말투 차이는 남을 수 있다. 목록 개수 같은 형식 경고와 이름 누락·조건 변경 같은 의미 오류를 구분해 검토한다. 제목 이름이나 줄바꿈까지 하나의 정답에 맞추지 않는다.

이 작업은 LLM 편집과 프롬프트 연결을 검증한다. 실제 사용자의 원음으로 STT와 함께 측정하거나 설치 앱의 외부 채팅창에서 삽입을 실사용 검증한 결과는 아니다. 기존 입력 경로는 수정하지 않았으며 설치·병합·푸시도 별도로 수행해야 한다. 글이 길어지고 프롬프트 예시가 늘면 모델의 처리 시간과 입력 토큰 사용량이 증가할 수 있다. 로컬 모델의 캐시 상태가 달라 단독 반복 실행의 시간과 이전 비교 실행의 시간을 직접 속도 개선 수치로 비교하지 않는다.

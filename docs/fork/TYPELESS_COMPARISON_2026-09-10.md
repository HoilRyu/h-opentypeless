**Typeless와 H-OpenTypeless 기능·품질 비교 — 2026-09-10**

결론: 우리 프로젝트는 기본 받아쓰기, LLM 다듬기, 번역, 선택 글 편집, 앱 감지, 사전 등 주요 기능의 골격을 이미 갖췄다. 큰 차이는 자동 개인화·교정 학습, 기록에서 재처리하는 경험, 한국어 명령 라우팅, 모바일 기능 일관성이다. 다듬기 품질은 프롬프트만으로 설명할 수 없다. STT의 실제 오류, 모델의 의미 보존 능력, 전달되는 문맥, 후처리·삽입까지 나눠 평가해야 한다.

로컬 기준은 `c311398`과 조사 시점의 깨끗한 작업 트리다. 코드와 기존 검증 기록을 읽고 Typeless 공식 홈페이지·도움말·가격표, OpenTypeless 소스, GitHub 이슈·토론, Reddit 글을 확인했다. 이번 조사에서 Typeless 앱을 직접 실행하거나 동일 음성을 양쪽에 입력하지 않았다. 따라서 아래의 ‘있음’은 공개 제품 설명 또는 코드 구현의 확인이며, 동등한 실사용 품질을 뜻하지 않는다. Typeless의 내부 STT/LLM 모델, 프롬프트, 학습 방식은 확인할 수 없다. 합성 예문과 기존 모델 비교도 실제 음성의 종단 간 벤치마크와 구분한다.

**현재 품질을 좌우하는 코드상의 지점**

첫째, STT에 사전이 전달되지 않는다. 예를 들어 처음부터 제품명이 다른 보통명사로 인식되면, LLM은 원음을 듣지 못한 상태에서 추측해야 한다. 사용자 사전을 지원되는 STT의 용어 힌트에 연결하고, STT 단계와 LLM 단계 각각에서 개선 여부를 측정하는 편이 좋다. 발음이 비슷하다고 무조건 치환하면 실제 사람 이름까지 바뀐다. 엔진별 지원 여부를 확인해 적용하고, 지원하지 않는 엔진에는 LLM 사전만 사용한다.

둘째, 일반 받아쓰기의 앱 문맥이 상당히 약해졌다. `prompt.rs`는 dictation일 때 family 설명과 app override를 건너뛰고 일반적인 문맥 사용 문장만 붙인다. 즉 사용자가 명시적 스타일을 선택하면 앱이 자동으로 격식을 바꾸지 않게 한 의도는 타당하지만, 앱별 자동 모드가 독립적으로 필요하다. ‘자동’을 별도 선택으로 두고 자동일 때만 앱별 형식을 사용하며, 최소/깔끔하게/구조화/전문적으로를 직접 선택하면 이를 우선하는 설계를 권한다. 기존 명시적 스타일 우선 정책을 되돌릴 필요는 없다.

셋째, 프롬프트가 이미 충분히 구체적이다. [현재 공통·스타일](../../src-tauri/src/llm/h_polish.rs)은 질문에 답하지 않기, 조건·부정·말투·식별자 보존, 자기 수정, 선택지 이름 보존, 번역을 다룬다. 단순히 더 긴 ‘Typeless 비슷한 프롬프트’를 추가하는 효과는 불확실하다. 사전 지침의 ‘Always use these exact spellings’와 공통 지침의 ‘해당 용어를 가리킬 때만 참고’를 한 조건부 규칙으로 정리하고, 무관한 사전 항목과 빈 섹션을 줄이는 실험부터 하는 것이 낫다. 전체 프롬프트를 축약하거나 영어로 바꾸는 것은 별도 평가 없이 기본값으로 적용하지 않는다.

넷째, 현재 출력 검증은 의미 검증이 아니다. [dictation_guard.rs](../../src-tauri/src/llm/dictation_guard.rs)는 빈 출력, 일부 reasoning 태그, 과도한 확장만 거부한다. `배포하지 마`가 `배포해`로 바뀌거나 `46235`가 `46236`으로 바뀌어도 이 검사만으로는 거부하지 못한다. 이는 코드 조건에서 도출한 예이며 이번에 모델이 그렇게 출력했다는 관측이 아니다. 번역 요청에는 이 dictation guard가 적용되지 않는다. 일반 받아쓰기는 검증 뒤 콜백으로 내보내므로, LLM 스트리밍 지원이 곧 실시간 최종문 삽입을 뜻하지도 않는다. [LLM 호출](../../src-tauri/src/llm/openai.rs)

다섯째, 데스크톱과 Android 로컬의 계약이 다르다. Android [DictationContract.java](../../android/app/src/main/java/dev/hoilryu/hopentypeless/mobile/DictationContract.java)는 맞춤법·추임새·중복 중심의 보수적 교정이고, 데스크톱에는 적극적인 구조화가 있다. Android 로컬은 별도 작은 모델, 4096 문맥·1536 출력 토큰 상한, 작업마다 모델 로딩이라는 제약도 있다. 원격 모바일은 데스크톱 프롬프트를 재사용하지만 앱 문맥은 general, 선택문 없음, 앱 매핑 장면 없음이다. 같은 음성이라도 세 경로가 같은 품질을 내리라고 기대하기 어렵다. [모바일 처리 코드](../../src-tauri/src/extensions/mobile/processing.rs), [Android 모드 설명](../../android/LOCAL_MODE.md)

여섯째, 평가 메타데이터가 부족하다. 현재 기록에는 원문·교정문·문맥·장면 등은 있지만, 요청별 STT/LLM 모델 digest·프롬프트 hash·편집 규칙 버전·단계별 지연을 일관된 평가 레코드로 남기는 구조는 아니다. 실패가 재현되려면 최종 조합 프롬프트와 실제 설정을 구분할 수 있어야 한다. 비밀키는 기록하지 않고, 평가에 쓰는 음성·문장은 사용자가 선택한 것만 로컬에 보관하는 방식을 권한다.

**이미 진행된 모델 비교를 어떻게 해석할 것인가**

[기존 비교 기록](LLM_MODEL_POLISH_COMPARISON.md)은 같은 프롬프트와 12개 전사문으로 Gemma4:12b/Qwen3.5:9b의 각 36개 출력, 총 72개를 비교했다. 이번 조사에서 재실행한 결과는 아니다.

| 기존 관측 지표 | Gemma4 12B | Qwen3.5 9B |
|---|---:|---:|
| 반말이 존댓말로 변한 실패 | 0/33 | 5/33 |
| 네 선택지 이름 보존 | 3/3 | 0/3 |
| 경로·숫자·포트 보존 | 3/3 | 3/3 |
| ‘쿠버’ 이름과 ‘정하지 말자’ 제안 말투를 함께 보존 | 0/3 | 3/3 |

이 표본에서는 Gemma 유지 판단이 합리적이다. 다만 Gemma도 ‘말자’를 ‘하지 마’로 바꾸는 요청 강도 문제가 남았다. 모델 크기·양자화가 다르고 표본이 작아 계열 전체의 우열은 말할 수 없다. 기존 문서의 정확도 0/33도 실제 실패가 없다는 뜻은 아니다. 다음 실험은 다른 모델을 무작정 늘리기보다 이 실패를 추가한 미사용 평가 문장으로 진행하는 편이 좋다.

**권장 프롬프트 조립 방식과 좁은 보완안**

`작업 계약 → 선택 스타일 또는 자동 앱 형식 → 관련 사전 → 명시적 개인 선호 → 2~3개 예시 → 최종 출력 언어`를 일관되게 구성한다. STT 전사문은 별도 메시지에 넣고 문자 경계를 이스케이프한다. 사용자 선호·장면은 작업 종류나 의미 보존을 바꿀 수 없게 한다. 이는 대부분 이미 구현되어 있으므로, 새 구조를 처음부터 만들기보다 빈 섹션·중복·충돌을 줄이는 변경으로 접근한다.

아래는 아직 제품에 적용하지 않은 보완 후보다. 기존 공통 규칙 중 말투 보존 부분을 명확히 하는 용도이며, 통째로 덧붙여 프롬프트를 늘리기보다 해당 규칙을 대체해 비교한다.

```text
화행을 보존한다. 질문·부탁·제안·명령·금지·추측·조건을 서로 바꾸지 않는다.
반말과 존댓말뿐 아니라 요청 강도도 유지한다.
‘하지 말자’를 ‘하지 마’로, ‘가능하면 해줘’를 ‘해줘’로,
‘할 수 있을까’를 ‘해줘’로 바꾸지 않는다.
조건을 해당 행동과 함께 보존한다. 문장을 목록으로 나누더라도 조건을 분리해 뜻을 바꾸지 않는다.
불확실한 고유명사는 사전에 비슷한 단어가 있다는 이유만으로 바꾸지 않는다.
```

다음은 사람이 작성한 목표 예이며 Typeless 또는 모델의 실제 출력이 아니다.

| 입력 | 목표 출력 | 지킬 점 |
|---|---|---|
| 쿠버라는 이름은 아직 정하지 말자 | 쿠버라는 이름은 아직 정하지 말자. | 제안을 명령으로 바꾸지 않기 |
| 가능하면 오늘 확인해주고 어렵다면 내일까지 해줘 | 가능하면 오늘 확인해주고, 어렵다면 내일까지 해줘. | 조건부 일정 유지 |
| 십오 명 아니 오십 명에게 보내고 초대장은 아직 보내지 마 | 50명에게 보내고, 초대장은 아직 보내지 마. | 명시적으로 바꾼 숫자만 반영, 금지 보존 |
| 최소 깔끔하게 구조화 전문적으로 네 가지를 넣어줘 | ‘최소’, ‘깔끔하게’, ‘구조화’, ‘전문적으로’ 네 가지를 넣어줘. | 선택지 이름과 개수 유지 |
| 이 문장을 요약해 달라는 요청을 적어줘 | 이 문장을 요약해 달라는 요청을 적어줘. | Dictate에서는 요청을 작성하기 |

ASR이 질문 억양을 잃은 짧은 문장은 텍스트만으로 평서/의문을 확정하기 어렵다. 이런 경우까지 예시로 억지 교정하면 다른 문장에서 오류가 생길 수 있다. 미묘한 말투는 원문 유지 우선으로 두고, 실제 음성을 포함한 평가로 개선 효과를 판단한다.

**검증과 복구 설계**

출력 검사에는 빈 출력·이유 설명 노출·잘림 종료 상태를 먼저 확인하고, 코드·경로·URL·명확한 숫자/단위 변경을 추가 점검한다. 단순 문자열 동일 비교는 ‘사십이→42’, ‘열 시→10시’, 명시적 숫자 수정까지 잘못 거부하므로 정규화와 자기 수정 예외가 필요하다. 부정·조건·요청 강도 전체를 정규식으로 보장하려고 하지 않는다.

의심 결과를 처리할 때는 원문/교정문을 비교하고 원문 사용 또는 재다듬기를 선택할 수 있게 한다. 기본 받아쓰기에 두 번째 LLM 검증을 항상 추가하면 지연과 비용이 증가하고 검증 모델도 틀릴 수 있다. 먼저 결정적인 검사와 회귀 평가를 강화하고, 실패 의심·사용자 재요청 때만 추가 처리하는 방식을 권한다. 현재 provider 호출 1회 계획도 있으므로 추가 호출은 별도 재처리 기능으로 설계한다.

기록에서는 ‘원문으로 다시 다듬기’를 먼저 구현하면 오디오 저장 없이도 LLM 품질을 비교할 수 있다. ‘같은 음성으로 다시 인식’은 별도 기능으로, 사용자가 고른 녹음의 보관·삭제 정책을 함께 마련한다. 실패했다고 이미 틀린 원문을 유일한 정답으로 확정하지 않도록 원문과 후보를 모두 보존한다.

**평가 계획 — Typeless와 실제 품질 차이를 확인하는 방법**

1. 한국어 실제 발화 100개 정도로 시작한다. 개발 요청 25, 짧은 대화·질문 15, 고유명사·영어 혼용 15, 자기 수정 15, 숫자·단위·부정·조건 15, 긴 열거 10, 작은 소리·잡음·무음 5처럼 범주를 나눈다. 이는 제안하는 구성이지 확보된 데이터가 아니다. 프롬프트에 사용한 문장은 최종 평가군에서 제외한다.
2. STT만 비교한다. 동일 음성에 대해 현재 Qwen/Whisper 후보의 원시 전사를 저장하고, 한국어 문자 오류율과 고유명사·숫자·부정 오류를 따로 센다. 지원 언어 고정과 자동 감지는 별도 조건이다.
3. LLM만 비교한다. 같은 원문·같은 사전·같은 앱 문맥·같은 프롬프트에 모델 또는 규칙 하나만 바꾼다. 먼저 기존 Gemma와 화행 보존 보완 후보를 비교한다. 모델 후보를 넓힐 때는 설치 가능성·메모리·지연을 함께 기록한다.
4. 전체 경로를 비교한다. Typeless와 H에 가능한 한 같은 오디오 입력 조건을 제공하고, 앱 종류·Typeless 플랜·언어 설정·개인화 상태를 기록한다. 파일 직접 입력이 안 되면 같은 녹음을 동일 장치 경로로 재생하는 등 시험 조건을 명시한다. Typeless의 내부 원시 STT를 얻지 못하면 Typeless는 최종 결과만 비교한다.
5. 원래 요청/조건/선택지가 빠지거나 새 사실을 넣으면 실패로 채점한다. 문장부호 취향과 의미 오류를 한 점수에 섞지 않는다. 자연스러움과 말투는 결과 출처를 가린 사람 평가로 판단한다. 임의의 ‘Typeless 대비 95%’ 같은 수치는 사용하지 않는다.
6. 녹음 종료→STT 완료→LLM 완료→삽입 완료의 p50/p95, 재교정 횟수와 최종 수동 편집량을 기록한다. 로딩 포함 첫 실행과 모델이 준비된 반복 실행, Android 원격/로컬을 분리한다. 치명적 사례는 최소 3회 반복하고 새 실패를 회귀군에 추가한다.

첫 배포 목표는 고정된 평가군에서 의미 추가·부정 반전·명령 실행·식별자 훼손 0건이다. 이는 유한한 평가군의 통과 기준이며 모든 실사용에서의 무오류 보장이 아니다. 출력 글머리표가 예쁜 것보다, 사용자가 다시 읽고 고쳐야 할 내용이 줄었는지를 우선한다.

| P1 | 특정 마이크 선택, 한국어 모바일 계약 통일 | 입력 품질을 안정화하고 데스크톱/모바일의 의미 보존 기준을 공유. 작은 모델에는 짧은 동등 계약 사용 |
| P2 | Android 선택 글 편집·번역 UI, 로컬 사전/선호 동기화 | 모바일에서도 데스크톱과 비슷한 작업 흐름 제공 |
| P2 | 선택 오디오 보관·재인식, 자동 개인화 | 사용자가 수정한 표현으로 후보 규칙을 만들고 확인·삭제·되돌리기 제공. 단일 수정에서 전역 선호를 추정하지 않음 |
| P2 | 검색 근거를 읽는 Ask | 필요할 때 검색 결과를 실제로 가져와 출처와 함께 답변. 현재 URL 열기와 구분 |
| P3 | iOS·기업 기능·광범위 지역화·클라우드 동기화 | 개인용 한국어 음성 입력의 핵심 품질이 안정된 뒤 확대 |

추천하는 다음 작업 묶음은 **실패 발화 평가 기반 마련 + 요청 강도 보존 개선 + 기록 재다듬기**다. 현재 Gemma·한국어 스타일 기반을 유지하면서 효과를 측정하고, 그 다음 STT 사전 연결과 한국어 명령 지원을 확장하는 순서가 적절하다. 이 문서는 조사와 제안만 추가했으며 제품 코드·사용자 설정·설치 앱은 변경하지 않았다.
